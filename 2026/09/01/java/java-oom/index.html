处理内存溢出和CPU 飙高

处理内存溢出和CPU 飙高

针对线上系统出现的 OOM（内存溢出）或 CPU 飙高问题，排查时需要遵循“先止血、后定位、再根治”的原则。以下是完整的排查思路和定位手段：

一、 线上 OOM（内存溢出）排查思路

OOM 通常表现为应用抛出 java.lang.OutOfMemoryError 异常、接口调用超时甚至进程被系统杀死10。

1. 确定 OOM 类型与现场保护

  • 查看日志：首先检查应用日志，确认是哪种内存溢出，常见的有 Java heap space（堆内存不足）、Metaspace（元空间不足）、Direct buffer memory（直接内存溢出）等10。
  • 获取 Dump 文件：如果提前配置了 -XX:+HeapDumpOnOutOfMemoryError，可以直接获取 OOM 发生时的内存快照（Heap Dump）；如果没有，可使用 jmap -dump:format=b,file=heap.hprof <pid> 手动抓取810。

2. 深入分析定位根因

  • 工具分析：使用 MAT (Memory Analyzer Tool)、JProfiler 或 VisualVM 等可视化工具打开 Dump 文件，定位“内存大户”（如大量未回收的对象、重复创建的大集合、未关闭的资源等）810。
  • 结合代码与 GC 日志：结合 GC 日志（如配置 -Xloggc）和监控平台（如 Prometheus+Grafana），分析内存增长趋势。追踪内存大户对象的创建链路，定位到具体的业务代码（例如：循环中拼接大 SQL 字符串、Druid 连接池的无限制缓存、静态集合未清理等）610。

3. 解决与预防

  • 解决：根据定位结果优化代码（如重构大对象拼接逻辑、关闭或限制框架缓存大小）、调整 JVM 参数（如调大 -Xmx 或 -XX:MaxMetaspaceSize）610。
  • 预防：建立内存监控与预警机制（如堆内存使用率 > 80% 触发告警），并在 Code Review 环节引入 SpotBugs 等静态分析工具28。

二、 线上 CPU 飙高排查思路

CPU 飙高往往由业务逻辑问题（如死循环）、频繁 GC 或上下文切换过多引起1。排查需要分层进行：

1. 宏观定位：确认 CPU 消耗在何处

  • 系统级排查

    指标：

    • us（用户态）高：说明业务代码本身在消耗 CPU。
    • sy（系统态）高：说明系统调用频繁或内核处理中断繁忙。
    • wa（I/O等待）高：说明 CPU 在等待磁盘响应（I/O 瓶颈），此时并非真正的 CPU 繁忙。
    • si（软中断）高：说明网络流量较高或定时器触发过于频繁35。

2. 微观定位：锁定具体进程与线程

  • 定位高 CPU 进程：通过 top -bn1 | head -20 或按 P 键排序，找到占用最高的进程 PID35。
  • 定位高 CPU 线程：使用 top -H -p <PID> 展开到线程级别，找到消耗 CPU 最高的线程 TID（注意区分进程级和线程级，避免被进程级数据欺骗）15。
  • 转换线程 ID：将找到的十进制 TID 转换为十六进制（printf '%x\n' <TID>）1。

3. 深入分析：结合堆栈与 GC 状态

  • 分析线程堆栈：使用 jstack <PID> | grep '<十六进制TID>' -C5 导出并搜索对应线程的调用栈。重点关注处于 RUNNABLE 状态的线程，观察其是否长时间停留在某个特定方法中（如死循环、复杂的正则匹配）13。
  • 排查频繁 GC：如果堆栈无明显异常，使用 jstat -gcutil <PID> 1000 观察 GC 频率。如果 Full GC 频繁且耗时极长，说明存在内存泄漏或大对象频繁创建，导致 GC 线程疯狂工作从而吃满 CPU110。

4. 特殊场景处理

  • 慢 SQL 导致：如果数据库 mysqld 进程 CPU 飙升，需通过 SHOW PROCESSLIST 或慢查询日志定位全表扫描、未命中索引的 SQL，紧急情况下可 KILL 掉慢查询9。
  • 内核/网络问题：若 sy 或 si 极高，可使用 vmstat 检查上下文切换（cs），或使用 perf、strace 等工具深入分析内核态消耗37。

总结：面对线上故障，第一步永远是固定现场（保存 Dump、导出 jstack 和 top 快照），避免重启服务导致线索丢失7。然后按照“系统指标 -> 进程/线程 -> 代码/GC”的链路逐步收敛，最终精准定位问题。

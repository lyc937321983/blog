百万级数据同步

百万级数据同步中台的核心方案为“全量分片批量 + 增量CDC实时”双轨策略，配合消息队列削峰、幂等去重与监控告警，可将同步耗时从小时级降至分钟级并保障数据一致性。 具体落地需按以下六个步骤执行：

1. 同步策略选型

根据数据量级与时效要求，采用“全量 + 增量”双轨策略：

  • 全量同步：适用于首次初始化或系统迁移。100万条数据不能一次性加载（否则容易OOM），需按主键范围分片，每批 1万~5万条 分批读取、分批写入。
  • 增量同步：日常运行采用 CDC（变更数据捕获）方式，通过数据库日志（如 MySQL Binlog、MongoDB Change Streams）实时捕获变更，延迟可控制在毫秒级，且对源库性能影响极小。

数据量大于10万条的源表，建议通过时间戳或日志解析抽取增量数据到增量分区表，而非每日全量刷新。

2. 整体架构设计

推荐采用 生产者 → 消息队列 → 消费者 三层解耦架构：

表格

层级 组件 作用
生产者层 源数据库 + 采集程序 全量分批读取 / CDC 捕获增量变更
消息层 Kafka / RabbitMQ 削峰填谷、解耦上下游、支持重试
消费者层 同步服务 + 中台写入模块 批量消费、幂等写入、异常处理

技术选型建议：

  • 消息队列：Kafka（高吞吐，适合大数据量）或 RabbitMQ（功能丰富，支持延迟队列和死信队列）
  • 采集工具：Debezium（CDC）、DataX（离线批量）、Flink CDC（流批一体）
  • 调度框架：XXL-JOB 或自研任务编排引擎，管理全量/增量任务的触发与依赖

3. 全量同步实现要点

  • 分片策略：按主键（如自增ID或ObjectId）范围分片，避免 skip/limit 带来的性能退化。例如100万条数据，每批2万条，共50个分片任务。
  • 并行处理：多个分片任务可并行执行，通过线程池或分布式调度框架控制并发度，避免压垮源库。
  • 批量写入：消费者端使用 bulkWrite / 批量 INSERT 操作，配合 ON DUPLICATE KEY UPDATE（MySQL）或 upsert（MongoDB）实现幂等写入。
  • 断点续传：记录每个分片的同步进度（如最后同步的主键ID），异常中断后可从断点恢复，无需重头开始。

4. 增量同步实现要点

  • CDC 监听：开启源库的 Binlog / oplog，通过 Debezium 等连接器实时捕获 INSERT / UPDATE / DELETE 事件。
  • 事件路由：将变更事件按业务实体路由到不同的消息队列 Topic，支持多下游消费。
  • 幂等保障：使用业务主键作为去重键，即使消息重复消费也不会产生脏数据。可通过唯一索引 + upsert 语义保证最终一致性。
  • 顺序保证：同一业务实体的变更消息需路由到同一分区（如按用户ID哈希），确保消费顺序。

5. 稳定性与可靠性保障

  • 限流：对源库读取和消息消费进行限流（如 RabbitMQ prefetch、Kafka max.poll.records），避免瞬时流量冲击。
  • 死信队列（DLQ）：消费失败的消息进入死信队列，支持人工排查后重新投递。
  • 监控告警：接入 Prometheus + Grafana，监控队列积压深度、同步延迟、失败率等关键指标，设置阈值告警。
  • 数据校验：同步完成后，通过行数比对、关键字段 checksum 等方式验证数据一致性。

6. 推荐执行步骤

  1. 评估源库：确认源数据库类型、表结构、数据量、是否有合适的索引字段用于分片
  2. 搭建消息队列：部署 Kafka/RabbitMQ 集群，创建全量队列和增量 Topic
  3. 开发全量同步任务：实现分片读取 → 消息推送 → 批量写入的完整链路
  4. 接入 CDC 增量同步：配置 Debezium 或类似工具，实时捕获变更并推送
  5. 压测验证：在测试环境模拟100万条数据同步，验证吞吐量、延迟和稳定性
  6. 灰度上线：先在低峰期执行全量同步，再切换到增量模式持续运行

️ 注意事项：全量同步期间对源库有一定读压力，建议在业务低峰期执行；避免直连业务库进行大批量查询，优先使用从库或 CDC 方式，降低对线上业务的影响。

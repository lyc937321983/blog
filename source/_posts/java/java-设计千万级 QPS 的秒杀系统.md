# 设计千万级 QPS 的秒杀系统

核心挑战在于应对瞬时高并发、资源竞争激烈以及严格的数据一致性要求，以下是系统性的架构设计方案：

### **一、 库存扣减方案：Redis 预扣减 + 消息队列异步同步**

在千万级 QPS 场景下，传统的数据库锁（悲观锁或乐观锁）会成为严重的性能瓶颈。业界主流且高效的方案是**“Redis 预扣减 + 消息队列异步同步”**，通过无锁高并发实现极致的吞吐量：

1. **活动前预热**：将商品库存从主库加载到 Redis 中（预扣库存），利用 Redis 单线程内存操作的高性能特性38。
2. **下单时原子扣减**：用户点击抢购时，直接在 Redis 中进行库存扣减。如果扣减成功，立即生成订单（状态为待支付），并将扣减消息发送到消息队列（如 Kafka/RocketMQ）38。
3. **异步落库**：后台服务从消息队列中消费消息，平滑地将库存变更同步到数据库。这实现了流量的“削峰填谷”，保护了底层数据库38。

### **二、 高并发下保证不超卖的机制**

超卖的本质是“非原子性操作”导致的并发冲突2。在上述方案中，防止超卖的核心在于保证 Redis 扣减操作的原子性：

1. **Lua 脚本打包操作**：将“检查库存是否大于0”与“扣减库存”这两个动作封装在 Lua 脚本中。Redis 执行 Lua 脚本具有原子性，执行期间不会插入其他命令，从而彻底杜绝超卖23。
2. **原子递减命令（DECR）**：也可以直接使用 Redis 的 `DECR` 命令进行扣减。该命令会直接返回扣减后的值，如果返回值小于 0，则说明库存不足，此时执行 `INCR` 回补库存并直接返回售罄38。
3. **兜底数据库乐观锁**：Redis 扣减成功后，在异步落库阶段，数据库层面仍需使用乐观锁（如 `UPDATE inventory SET stock = stock - 1 WHERE product_id = ? AND stock > 0`）作为最后一道防线，确保数据的最终一致性35。

### **三、 Redis 挂了怎么办？（高可用与容灾策略）**

在秒杀这种核心链路中，Redis 绝不能是单点。必须通过高可用架构和降级策略来应对故障：

1. 自动故障转移（高可用架构）：
   - 部署 **Redis Sentinel（哨兵模式）** 或 **Redis Cluster（集群模式）**。当主节点挂掉时，Sentinel 会自动将从节点升级为主节点，整个过程自动完成，无需人工干预，保证服务不中断14。
2. 数据恢复与持久化：
   - 开启 **AOF（Append Only File）** 或 **RDB（快照）** 持久化机制。当服务器重启或节点恢复后，可以通过加载最新的 AOF 日志或 RDB 文件来恢复内存数据14。
3. 熔断降级与快速失败：
   - 如果 Redis 集群彻底不可用或响应极慢，系统必须触发**熔断机制**，防止请求堆积拖垮整个后端服务。
   - 此时可快速降级到“返回售罄”的静态页面，或者提示“活动太火爆，请稍后再试”，牺牲部分用户体验以保全系统整体稳定3。
4. 兜底数据重建：
   - 在极端情况下（如数据丢失且无法通过持久化恢复），可以通过定时对账任务，以数据库中的真实库存为基准，重新将数据同步加载到 Redis 中，恢复缓存状态13。

**总结**：千万级秒杀系统的核心设计思路是：**前端限流拦截，请求队列削峰；Redis Lua 脚本原子扣减防超卖；服务无状态化应对高并发；最后通过 Redis 集群高可用与熔断降级兜底，保证系统的韧性。**
